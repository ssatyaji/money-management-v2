# Plan: Fix Registration OTP Verification Flow

**Nomor Plan:** 2  
**Tanggal:** 2026-06-17  
**Status:** PENDING  
**Prioritas:** HIGH — Security Bug

---

## Latar Belakang & Masalah

Fitur registrasi memiliki **3 bug kritis** yang menyebabkan:
1. OTP email tidak terkirim ke user (SMTP tidak terkonfigurasi)
2. User bisa langsung masuk ke dashboard tanpa melakukan verifikasi OTP
3. Method `verifyOtp` di backend crash karena memanggil `usersService.update(null, ...)` — logic yang tidak pernah selesai ditulis

---

## Daftar Bug & Root Cause

### BUG-1: Email OTP Tidak Terkirim
- **File:** `backend/.env` (baris 12-13)
- **Root Cause:** `MAIL_USER` dan `MAIL_PASS` kosong, sehingga `MailService` tidak membuat transporter SMTP dan hanya mencetak log ke console.
- **Bukti:** `mail.service.ts` baris 16: `if (user && pass)` → jika keduanya kosong, transporter tidak dibuat.

### BUG-2: Dashboard Bisa Diakses Tanpa Verifikasi Email
- **File:** `frontend/src/app/(dashboard)/layout.tsx`
- **Root Cause:** Dashboard layout hanya mengecek `isAuthenticated`, **tidak mengecek** `user.isEmailVerified`. Setelah registrasi, backend langsung mengembalikan access token (meskipun email belum diverifikasi), sehingga frontend langsung set `isAuthenticated = true`.
- **Alur bug:**
  1. User daftar → backend buat user + kirim token
  2. Frontend set `isAuthenticated = true`
  3. User bisa navigasi ke `/dashboard` tanpa OTP sama sekali
  4. Dashboard layout hanya cek `isAuthenticated` → user masuk

### BUG-3: Method `verifyOtp` Backend Rusak (Broken Code)
- **File:** `backend/src/modules/auth/auth.service.ts` (baris 203–207)
- **Root Cause:** Kode di dalam blok `if (purpose === 'REGISTER')` memanggil `this.usersService.update(null as any, ...)`. Ini jelas kode yang tidak selesai ditulis (ada komentar `// Wait, usersService.update takes id as first param`). Ini akan menghasilkan error runtime jika dipanggil via endpoint `POST /auth/verify-otp`.
- **Catatan:** Endpoint ini dipanggil oleh halaman verify-email ketika user **tidak** sedang login (fallback path di `verify-email/page.tsx` baris 45).

```typescript
'use client';

import { useAuth } from '@/providers/auth-provider';
import { useRouter } from 'next/navigation';
import { useEffect, useState } from 'react';
import { AppSidebar } from '@/components/layout/sidebar';
import { AppHeader } from '@/components/layout/header';
import { MobileNav } from '@/components/layout/mobile-nav';

export default function DashboardLayout({ children }: { children: React.ReactNode }) {
  const { isAuthenticated, isLoading, user } = useAuth();  // ← tambah 'user'
  const router = useRouter();
  const [sidebarOpen, setSidebarOpen] = useState(false);

  useEffect(() => {
    if (isLoading) return; // Tunggu hingga auth state selesai dimuat

    if (!isAuthenticated) {
      // Tidak login → ke halaman login
      router.push('/login');
      return;
    }

    if (!user?.isEmailVerified) {
      // Sudah login tapi belum verifikasi email → ke halaman verify-email
      router.push(`/verify-email?email=${encodeURIComponent(user?.email ?? '')}`);
      return;
    }
  }, [isAuthenticated, isLoading, user, router]);

  // Tampilkan loading spinner selama auth state dimuat
  if (isLoading) {
    return (
      <div className="min-h-screen flex items-center justify-center bg-background">
        <div className="flex flex-col items-center gap-4">
          <div className="w-10 h-10 border-3 border-primary/30 border-t-primary rounded-full animate-spin" />
          <p className="text-sm text-muted-foreground animate-pulse">Memuat...</p>
        </div>
      </div>
    );
  }

  // Jangan render konten jika tidak terautentikasi atau belum verifikasi email
  if (!isAuthenticated || !user?.isEmailVerified) {
    return null;
  }

  return (
    <div className="min-h-screen bg-background">
      {/* Desktop Sidebar */}
      <AppSidebar isOpen={sidebarOpen} onToggle={() => setSidebarOpen(!sidebarOpen)} />

      {/* Main Content */}
      <div className={`transition-all duration-300 ${sidebarOpen ? 'lg:ml-64' : 'lg:ml-20'}`}>
        <AppHeader onMenuToggle={() => setSidebarOpen(!sidebarOpen)} />

        <main className="p-4 md:p-6 lg:p-8 pb-24 lg:pb-8">
          {children}
        </main>
      </div>

      {/* Mobile Bottom Nav */}
      <MobileNav />
    </div>
  );
}
```

#### Penjelasan perubahan:
- Tambah `user` dari `useAuth()` (sebelumnya tidak diambil)
- Di `useEffect`, tambah kondisi: jika `!user?.isEmailVerified` → redirect ke `/verify-email?email=...` (dengan email sebagai query param agar halaman verifikasi tahu email yang perlu diverifikasi)
- Di blok `if (!isAuthenticated)` → tambah `return null` agar tidak render konten dashboard

## Catatan Tambahan

### Mengapa Backend Tetap Mengeluarkan Token Saat Register?
Saat ini, backend mengeluarkan access token + refresh token langsung setelah registrasi (sebelum verifikasi email). Ini diperlukan agar frontend bisa:
- Menyimpan state user yang baru terdaftar
- Menggunakan endpoint `POST /auth/verify-email` (yang butuh auth token) untuk memverifikasi email

Strategi keamanan yang kita gunakan adalah **token dikeluarkan tapi akses dashboard diblokir di frontend** selama `isEmailVerified = false`. Ini adalah pendekatan yang pragmatis dan tidak memerlukan refactor besar pada backend.

> Alternatif yang lebih secure (out of scope plan ini): Backend tidak mengeluarkan token sampai email diverifikasi, dan verifikasi OTP dilakukan via endpoint public dengan email+kode saja.

### Mengapa Tidak Perlu Ubah Backend Guard/Middleware?
Backend sudah memiliki `isEmailVerified` di response data user. Perlindungan di frontend sudah cukup untuk use case ini karena:
1. Data sensitif tetap diproteksi oleh JWT di backend
2. Akses dashboard bersifat UI-only — API calls tetap memerlukan token yang valid
3. Token tetap diperiksa oleh JWT guard di setiap request backend
